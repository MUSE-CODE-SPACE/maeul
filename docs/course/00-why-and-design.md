# 레슨 0 — 왜 만드는가, 그리고 설계 원칙

## 문제: 게임 NPC는 아직도 둘 중 하나다

게임 속 마을 주민에게 말을 걸면, 대개 이렇다.

1. **정해진 대사 트리** (Yarn Spinner 등) — 살아있지 않다. 세 번 말 걸면 세 번 똑같다.
2. **클라우드 NPC SaaS** (Inworld, Convai 등) — 살아있지만 **폐쇄형이고, 대화마다 과금**되고, 인터넷이 끊기면 죽는다.

두 방식 다 인디 개발자에게는 아프다. 스크립트는 노동이 무한하고, SaaS는 돈과 종속이 무섭다.

## 우리가 노리는 빈자리

> **LLM처럼 즉흥적이면서, 오픈소스이고, 공짜이고, 오프라인이고, 내 게임의 세계관을 아는 NPC 엔진.**

이게 Maeul이다. 그리고 이건 실제로 아직 결정판이 없는 니치라, **잘 만들면 GitHub에서 깃발을 꽂을 수 있다.** (강좌 마지막 레슨에서 홍보까지 다룬다.)

## 설계 원칙 4가지

이 원칙들이 이후 모든 코드 결정을 지배한다. 외워두자.

### 원칙 1 — 돈이 안 든다 (Money-free by default)
기본 백엔드는 **로컬 모델**(Ollama)이다. 우리는 코드에서 OpenAI 호환 API 규격을 쓰지만,
그건 *전선 규격*일 뿐 OpenAI에 돈을 내는 게 아니다. Ollama·llama.cpp·LM Studio가 다
이 규격을 말하므로, 같은 코드가 로컬 무료 모델에 그대로 붙는다. 유료 호스티드는 **옵션**이다.

> 초보가 가장 많이 하는 오해: "OpenAI 호환 = OpenAI 요금". 아니다. 규격 이름일 뿐이다.

### 원칙 2 — 코어는 의존성 0
`import maeul`의 코어는 **표준 라이브러리만** 쓴다. 캐릭터는 JSON으로, 백엔드 호출은
`urllib`로, RAG는 순수 파이썬 TF-IDF로. 무거운 패키지(numpy, torch)도, 임베딩 모델
추가 다운로드도 필요 없다. `pip install maeul` 하면 바로 돈다. (YAML·서버는 옵션 extra.)

가벼움은 채택률로 이어진다. 게임 개발자는 무거운 파이썬 스택을 게임에 끌어들이기 싫어한다.

### 원칙 3 — 게임이 먹는 건 텍스트가 아니다
NPC의 한 마디는 대사 문자열 하나가 아니라 **구조**다: 무슨 말을 하고(`line`), 어떤
감정이며(`emotion` → 표정·애니메이션), 무슨 행동을 하고(`action`), 어떤 주제인가(`topic`).
엔진은 이 구조를 소비한다. 그래서 우리는 항상 구조화 JSON을 돌려준다. (레슨 1)

### 원칙 4 — 데이터 주도
주민의 성격은 코드가 아니라 **파일**이다. 기획자가 프로그래머 없이 새 주민을 추가할 수
있어야 한다. 성격·말투·공포·관계·지식을 카드(JSON/YAML)로 뺀다. (레슨 3)

## 전체 그림

```
① 캐릭터 카드   성격·말투·공포·관계·지식          (데이터)
② 월드 컨텍스트  시간·날씨·계절·이벤트(재해!)      → 그날그날 다른 이야기 / 홍수 땐 무서움
③ 기억          단기(오늘) + 장기(바운디드)
④ RAG 로어      게임 세계관 지식 + 로컬 검색       → 궁금증에 고증된 답
⑤ 대사 디렉터   ①~④ 조립 → 모델 호출 → 구조 파싱   ← 엔진의 심장
⑥ 서버/어댑터   HTTP · Unity · (웹/임베디드 로드맵)
```

이후 레슨은 이 그림을 **아래에서 위로** 쌓는다: 스키마(⑤의 출력) → 백엔드 → 카드 →
월드 → 기억 → 로어 → 디렉터 → 서버 → 유니티.
